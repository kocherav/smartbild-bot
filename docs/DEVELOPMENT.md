# Разработка и тестирование

## Обязательный порядок

1. Прочитать `telegram-bridge/docs/architecture/VERIFIABLE_REALITY_PROTOCOL.md`.
2. Описать конечный бизнес-результат и полный маршрут.
3. Воспроизвести дефект и добавить регрессию на границе модулей.
4. Исправить общий класс проблемы, не конкретный номер сделки.
5. Выполнить затронутые тесты и полный quality gate.
6. Для пульта выполнить browser checks.
7. Записать факты и ограничения в архитектурный `CHANGELOG.md`.
8. После выпуска проверить SHA и разрешённые внешние этапы read-back.

Критерии: QA-2026-10-12 и QA-2026-10-14 в `TEST_MATRIX.md`.

## Уровни доказательства

- **Реализовано** — код изменён.
- **Проверено изолированно** — тесты прошли без внешних систем.
- **Выпущено** — проверенный SHA загружен в процесс.
- **Подтверждено в работающей системе** — реальный вход и каждый внешний результат подтверждены.

СИНТЕТИЧЕСКИЙ тест не подтверждает бизнес-результат.

## Тестовые контуры

- `telegram-bridge/test_*.py` — диалоги, маршрутизация, очередь, устойчивость;
- `megaplan-crm/test_*.py` — сделки, документы, деньги, закупки, монтаж;
- `hogart-scraper/test_*.py` — API, КП и Excel;
- `daichi-scraper/test_*.py` — кэш каталога;
- `hogart-scraper/dashboard/tests` — API/UI и браузер;
- `offline_tests.py` — изолированный сборщик;
- `quality_gate.py` — тесты плюс соответствие SHA.

## Инварианты кода

- Внешний эффект выполняется после preview/подтверждения, когда оно требуется.
- Каждая запись имеет ключ повтора и отдельную квитанцию.
- Неизвестный результат сначала проверяется read-back.
- Worker не переключает текущий диалог.
- Callback содержит ID объекта, а не зависит от глобальной «текущей сделки».
- Деньги — Decimal/копейки, не float как источник истины.
- Успешный этап сохраняется при падении следующего канала.
- Новый общий случай не реализуется одноразовым `finance/tools`-скриптом.
- Тест не ослабляется ради зелёного результата.
