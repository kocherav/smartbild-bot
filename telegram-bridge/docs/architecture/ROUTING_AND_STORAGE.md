# Входы, приоритеты и источники данных

## Включённая архитектура после ARCH-010

1. Один poller сохраняет входящее событие до подтверждения offset. Callback-подтверждения поддерживаются: связаны с владельцем, экраном и одноразовым токеном. Текст, похожий на кнопку подтверждения, запись не разрешает.
2. Роль монтажника проверяется по настроенному Telegram chat ID. Его сообщения не попадают в обработчики руководителя; файлы принимаются только в открытый отчёт.
3. Основной процесс выполняет короткую маршрутизацию. Получение/разбор файлов и обращения к CRM запускаются отдельно; два независимых канала модельного разбора документов, отдельная очередь разработчика.
4. Каждое сообщение связывается со снимком UI и ревизией. Старый процесс не меняет новую выбранную сделку. Готовый счёт может попасть в очередь, но не переключает текущий экран.
5. Финансовые/CRM-записи выполняются через журнал операций; повтор подтверждения возвращает квитанцию. Неизвестный результат требует сверки, а не нового create. `reconcile_operations.py` и RECOVERY.md описывают восстановление.
6. Приёмка монтажного отчёта сохраняет начисление и задачу публикации одной транзакцией. Excel/CRM/OneDrive обновляются отдельно. Архив оригиналов использует защищённую локальную очередь.
7. Обновление кода, запрошенное из режима разработчика, применяется между пакетами событий после завершения дочерних задач. Почта — раз в час; локальные очереди — раз в 30 секунд; неудачная файловая публикация — повтор не ранее пяти минут.
8. Запрос `/status` читает журнал без переключения UI. Почтовое уведомление не меняет диалог: подтверждение открывается через сохранённую очередь «Банковские уведомления». Часовой интервал хранится между перезапусками.
9. Фоновый переход сделки в монтаж/закупку захватывает свободный UI по ожидаемой ревизии; новое сообщение во время CRM-запроса откладывает этот переход.

Совместимость сборного отчёта: `legacy_report_plan.py`, `legacy_report_commit.py` и `legacy_report_ui.py` подключены в исходниках к старому маршруту Telegram; включение фиксируется отдельно в CHANGELOG. Подтверждённые работы сохраняются атомарно по сделкам, исходник остаётся в защищённом хранилище. Обновление сводного реестра выполняется из неизменяемого задания `legacy_ledger_jobs`, а не повторным разбором диалога. Это ещё не полное объединение исторических выплат и нового кабинета: решение Q-PAY-02 ожидается.

## Исходная карта A1 — исторический срез до изменений

Следующие разделы сохранены для аудита исходной системы; описанные здесь ограничения callback/ролей/блокировок заменены включённой архитектурой выше. Актуальные строки обработчиков находятся в генерируемых индексах.

Срез кода 2026-09-29. CURRENT_CODE_MAP.md / INVENTORY.json содержат конкретные строки, функции, статические кнопки и условия. STATE_ROUTES.json сопоставляет именованные состояния сценариям и читателям/писателям. Динамические записи перечислены отдельно, а не выданы за постоянные состояния.

## Входной порядок

1. Telegram getUpdates: message с text/document/photo/video; callback_query и голосовые сообщения в этой версии не являются поддержанными входами.
2. Проверка роли: владелец, разрешённое имя монтажника, получатель ЭДО. Последний только регистрирует канал уведомлений.
3. Video: только активный монтажный отчёт; иначе отказ.
4. Photo: активный монтажный отчёт → вложение; монтажник без отчёта → отказ; владелец вне отчёта → модельный путь. Явного отдельного маршрута фотографии карточки/счёта здесь нет — расхождение с возможностями document.
5. Document: сохранение/конверсия → снимок состояния; порядок специализированных обработчиков указан ниже.
6. Text: глобальное меню владельца → плательщик → накопительное выполнение → отдельная ветка монтажника → help/start → банк → сделки → прямые команды счета/экономики → ИИ.
7. ИИ: fork + общая блокировка → ответ → извлечение протоколов → серверные функции → очистка служебных маркеров → отправка. Вложенный поиск каталога может вызвать дополнительные модельные раунды.

## Динамические меню

- Сделки: deal_selection_keyboard; варианты по текущей выборке и выбранному фильтру.
- Разрешённые статусы: переходы из API, сохранённые в state.transitions.
- Банковские операции, сделки-кандидаты: handle_bank_ui, локальные идентификаторы/словари выбора.
- Счета клиента: invoice_download; варианты по API.
- Проекты: project_selection_keyboard; file_id и набор выбранных файлов.
- Контакты: installation_contact_keyboard; ID контакта, отдельный путь создания.
- Монтажные объекты/история: main; ID из installation_choices/history.
- Исключения старых отчётов: installer_exception_keyboard; уточнение объекта/суммы/позиции.
- Счета закупки, поступления, распределения и компенсации: handle_deal_ui; сохранённые choices и номера строк.
- Подтверждения создаются также локальными словарями keyboard внутри функций. Они включены в ветвления исходного индекса; не считать 46 глобальных клавиатур полным числом экранов.

## Дополнительные входы вне основного меню

- /start, /help, /menu, /deals, /dev_status; /счет|счёт|invoice, /сделка|deal, /экономика|economics|profit.
- HOGART_SEARCH, DAICHI_SEARCH: чтение каталога; UPDATE_KEMIX_PRICES: изменение локального прайса после согласования.
- BUILD_KP, CREATE_MEGAPLAN_DEAL, SYNC_DEAL_KP, SUPPLIER_INVOICE_APPLY, PAYER_CARD_APPLY, APPLY_WORK_STATEMENT: команды модели, не самостоятельное разрешение на запись.
- ATTACH_FILE / ATTACH_IMAGE_URL: доставка файла/изображения; обязателен контроль допустимого источника и роли.
- Прямой webhook megaplan_webhook.py предназначен для получения/отправки счёта, не является универсальным журналом событий CRM.
- Периодические проверки КП и закупки/монтажа — раз в минуту; почта — раз в час. Каталог Daichi обновляется отдельным таймером (живой таймер проверить на A9, не утверждается здесь).
- Административные скрипты миграции, синхронизации договора, перевыпуска ИП не являются кнопками Telegram и не должны запускаться общей моделью без отдельного сценария.

## Источники истины и зависимости

| Данные | Текущие источники | Необходимая граница |
|---|---|---|
| Клиент/плательщик/продажа/стадия | Мегаплан + локальный кеш | Писать по ID, перед записью читать актуальное |
| Диалог | deal_ui_state.json на chat_id | Не является журналом завершённых бизнес-операций |
| Разбор счёта | document_jobs.json и сохранённый оригинал | Задание привязано к файлу и сделке |
| Закупка, остатки, компенсации | procurement_registry.json | Защита от параллельного распределения, реестр источников |
| Плановые затраты | Deal ledger + financial_amount_overrides.json + валюта | Явная база unit/line_total, не эвристическая правка |
| Монтаж | SQLite installation_workflow + старые реестры | Начисление и выплата раздельно, повтор не начисляет |
| Документы | локальные файлы, вложения Мегаплана, OneDrive | Три независимых результата сохранения/доставки |
| Свободный диалог | сессия модели | Не заменяет подтверждённые данные операции |

## Решения по старым конфликтам

- Создание КП не разрешает автоматически создавать сделку: правило пользователя имеет приоритет над устаревшими HELP_TEXT/комментариями.
- Передаются только утверждённые руководителем монтажные работы, а не автоматически все работы сделки. Полная ведомость для проверки руководителем и передаваемая редакция — связанные, но разные стадии.
- Исторические записи монтажа не означают завершённую сделку. Миграция не должна повторять начисления; массовая смена статусов не выполняется ради проверки.
- Перечень закупок, экономика и реестры требуют обновления после подтверждённого изменения; ошибка архива не разрешает повторно применять финансовую запись.

## Разрешение динамических записей состояния

Четыре нелитеральных записи из STATE_ROUTES.json: pending_now восстанавливает supplier_invoice_confirm из очереди; next_step в двух местах выбирает deal_create_client либо deal_create_items; pending в обработке поиска выбирается из словаря режимов поиска. Идентификаторы поиска и динамические значения пользовательского выбора хранятся в state и перечислены в индексах кода. Число 89 относится к непосредственно назначаемым строковым состояниям, а не ко всем возможным значениям pending.

Граница завершения A1: маршруты и их владельцы проиндексированы, шаблоны и хранилища описаны, противоречия выделены. Сквозная работоспособность этих маршрутов проверяется A3/A9, а не объявляется на основании чтения.
