# Восстановление без повторной финансовой записи

## Фоновая публикация и архив

`megaplan-crm/archive_outbox` содержит защищённые исходники и SQLite-очередь. Временный исходник можно удалить после подтверждённого сохранения в очереди; сам каталог очереди удалять нельзя. Доставка повторяется только для файлов, не для оплат или начислений. Ошибки повторяются не чаще одного раза в пять минут.

Монтажная публикация хранит существующий ID комментария и сначала обновляет его. Исключение: API подтвердил 403 и GET того же комментария той же сделки показывает только `act_read`. Тогда создаётся новая версия с сохранением ссылки на предыдущую в журнале. Старый файл не удаляется. Это ограничение прав Мегаплана, а не повтор при тайм-ауте. При неизвестном результате любого создания поле `publication_create_state=uncertain` блокирует новое создание. Оператор должен проверить комментарии нужной сделки через API, найти именно созданную ведомость и зафиксировать её ID. Сбрасывать признак до полной сверки нельзя. Финансовая приёмка при этом уже сохранена и повторно не проводится.

Для проверки используйте `megaplan-crm/reconcile_publications.py installation DEAL_ID` либо `economics DEAL_ID`. Утилита обращается только к GET комментариев указанной сделки и ищет точный сохранённый ID файла. При единственном совпадении восстанавливает локальную квитанцию; при отсутствии или нескольких совпадениях не меняет маркер и не разрешает новое создание. Никакие удалённые документы этой командой не создаются и не удаляются.

Исходники монтажных отчётов сохраняются в `megaplan-crm/report_sources` до подтверждения получения. Очередь `report_publications` доставляет их в OneDrive отдельно от отправки отчёта руководителю. Снимок SQLite сохраняет ссылки/статусы, но **не заменяет резервное копирование самих каталогов исходников** (`report_sources`, `archive_outbox`). Их нельзя очищать как временные файлы.

## Неопределённый результат

В Telegram владелец может спросить `/status` или «Что сейчас делает бот?». Это чтение зарегистрированных операций и этапа обработки счёта: оно не меняет выбранную сделку, не отменяет обработку и не запускает повтор. При `нужна сверка результата` используйте код проверки для процедуры ниже.

Таймаут не означает, что Мегаплан ничего не сохранил. Операция получает статус `uncertain`; повтор того же намерения не вызывает API записи.

1. `python3 reconcile_operations.py list` — ID, сценарий, целевые объекты, версия и статус, без полного входного документа.
2. `show OPERATION_ID` — детали, только в защищённой локальной среде. Вывод может содержать бизнес-данные; не пересылать журналы целиком.
3. Прочитать фактический объект/журнал внешней системы. Проверить ID, клиента, плательщика, сумму, позиции и результат всех этапов. Отсутствие объекта в неполной поисковой выдаче не доказывает отсутствие записи.
4. При подтверждённом полном успехе: `resolve ID --revision N --actor operator --outcome succeeded --evidence 'основание проверки и внешний ID' --receipt /защищённый/путь/receipt.json`. Квитанция содержит `ok: true` и проверенные поля результата исходного обработчика. Повтор в боте возвращает её без новой записи.
5. Если доказано, что внешней записи нет: `--outcome failed` с описанием проверки. Это закрывает старое намерение; новая попытка требует нового просмотра и подтверждения. Нельзя выбирать failed для частично созданного объекта.
6. При частичном успехе исправлять только недостающие этапы после проверки. Не создавать второй объект и не удалять первый как «откат» без основания.

Утилита не обращается к API записи. Журнал сверки неизменяемо дополняется событием; сверить работающую операцию нельзя. На старте прерванные running переводятся в uncertain, не исполняются заново.

## Монтаж: приёмка и публикация

Сборный отчёт сохраняет принятие всех затронутых сделок, исходник и `legacy_ledger_jobs` одной транзакцией. Задание содержит фиксированную сумму взаиморасчётов и оригинал с SHA-256; оно не принимает новый ввод из чата. Если сводный JSON-реестр недоступен, повторяется только его обновление. Повтор после сохранения реестра, но до квитанции, распознаётся по хешу исходника; другая сумма того же отчёта блокируется. Старые выплаты при этом не пересчитываются. `retry_publications` обрабатывает и эти задания, с задержкой после ошибки не менее пяти минут.

У очереди исходников `report_publications` есть ревизия: возврат/повторная отправка/приёмка во время загрузки не теряются после завершения старого задания. Менеджерская очередь берётся из статусов отчётов в SQLite и не зависит от успешности Telegram-уведомления.

Приёмка, фиксированная сумма и постановка publication_jobs сохраняются одной транзакцией. Ошибка Excel, OneDrive или Мегаплана не отменяет начисление. Фоновый retry_publications строит только производные файлы; не принимает отчёт и не платит повторно. Новое изменение увеличивает ревизию очереди, поэтому завершение старой публикации не теряет новое событие. После ошибки — пауза минимум пять минут.

## Входящие сообщения и файлы

Операторские уведомления не должны напрямую вызывать Store.keyboard для занятого пользователя: этот метод деактивирует предыдущий экран. Пользоваться send_message с активным runtime-контролем либо отправлять уведомление без клавиатуры. Если оператор уже вытеснил экран, сначала прочитать pending и сохранённый черновик; по просьбе пользователя переиздать именно текущий экран, не менять pending и не запускать разбор заново. 30.09.2026 так восстановлен installer_report_objects: состояние до/после идентично, Telegram message_id 2421.

Telegram update сохраняется в incoming до продвижения offset. Это журнал для сверки, а не очередь слепого повторного исполнения. Прерванный разбор счёта получает needs_retry; исходный файл сохранён, повтор доступен в закупке. Сохранённые preview и счета в очереди не переносятся в другую выбранную сделку.

Новые входящие проходят состояния routing → routed. Если процесс прерван внутри маршрутизации, при старте запись получает needs_review; `/status` показывает необходимость сверки и перехода к сохранённому черновику. routed означает только передачу обработчику, не финансовый успех фонового работника. Последний проверяется в operations/document_jobs. Старые записи received не помечаются задним числом как ошибки.

## Версия комплекта ЭДО

Перед доставкой проверяются фактический PDF договора, его принадлежность сделке, ИНН обеих сторон, номер/дата; каждый счёт сверяется по ID сделки, плательщика и нашей организации. Комплект получает неизменяемый fingerprint в delivery_bundles. Если документы поменялись после частичной отправки, продолжение блокируется: нужен новый явно отправляемый комплект. Квитанции отдельных каналов не переносятся между версиями. Повреждённый реестр доставки не заменяется пустым.

## Откат приложения

Штатный проверенный reload не завершает активных работников. Пока он ожидает их окончания, новые периодические проверки не запускаются; входящие сообщения обслуживаются. Запрос привязан к SHA всего проверенного комплекта Python. Последующие правки требуют нового тестирования и запроса; повреждённый/устаревший запрос не приостанавливает фон бессрочно.

Исходники до изменений: architecture-backup-rInsrt/python-sources.tar.gz. Снимки данных — отдельные приватные architecture-state-* с manifest/SHA. Откат кода не означает откат финансовых реестров. Нельзя восстановить старый JSON/SQLite поверх новых подтверждённых платежей. Перед обслуживанием дождаться отсутствия активных пользовательских работников, сделать снимок и проверить журнал операций.

## Границы проверки

Изолированные тесты запрещают сеть, дочерние процессы, внешние записи и чтение секретов. Они проверяют сценарии и отказы, но не гарантируют доступность внешнего сервиса. Реальные тестовые платежи, заказы и сделки для приёмки не создаются.
