# Автономный QA-агент SmartBild

## Назначение

Агент регулярно проверяет четыре проекта SmartBild, превращает подтверждённые сбои в дедуплицированные задачи разработчику и хранит связь «прогон → доказательство → дефект → исправление → повторная приёмка». Он не выполняет хозяйственные операции, не рассылает документы и не выпускает код самостоятельно.

## Контур

1. **Инвентаризация:** карта сценариев, входов, ролей, состояний, фоновых событий, хранилищ и внешних эффектов берётся из `SCENARIOS.md`, `STATE_ROUTES.json`, `CURRENT_CODE_MAP.md` и фактического кода.
2. **Профили:** быстрые модульные проверки запускаются при изменении; полный `quality_gate` — перед выпуском; browser runner — при изменениях пульта. Живые проверки выделяются в отдельный read-only профиль и не подменяют офлайн-допуск.
3. **Оракулы:** проверяется конечный бизнес-результат, а также деньги, количество, единицы, НДС, версии, идемпотентность, сохранение уже успешных этапов и рабочее продолжение из каждого состояния.
4. **Триаж:** ошибка теста, нарушение изоляции, skip и отсутствие квитанции считаются дефектом. Повторы одного набора падений объединяются по устойчивому fingerprint.
5. **Передача:** для каждого дефекта формируется задача с приоритетом, точной квитанцией, упавшей границей и обязательным протоколом QA-2026-10-14. Передача агенту-разработчику выполняется существующим режимом «Задача разработчику» либо внешним worker, который забирает текст командой `prompt`.
6. **Исправление:** разработчик сначала добавляет воспроизводящую регрессию, исправляет общий класс причины, выполняет локальные и полные проверки. QA-агент повторяет исходный профиль на новой версии.
7. **Выпуск:** отдельный release-контур проверяет SHA-квитанцию, browser/сквозные доказательства и отсутствие P0/P1. Safe reload и живая проверка не являются полномочием QA-агента.

## Передача разработчику

QA-задача сначала получает статус `ready`. Бот показывает владельцу краткую карточку без технического шума: приоритет, маршрут, суть и число повторов. Полная квитанция остаётся в реестре.

- `✅ Передать разработчику QA-…` атомарно переводит карточку в `approved` и запускает существующий Codex worker ровно один раз.
- `🚫 Не передавать QA-…` переводит её в `dismissed`; разработчик не запускается.
- Worker получает полный prompt и lease `fixing`. После работы статус — `awaiting_verification`, но не `closed`.
- QA повторяет исходный человеческий маршрут. Только новый успешный результат может закрыть дефект.
- Технические решения принимает разработчик. Владельцу через `decision_channel` передаются только реальные бизнес-неоднозначности.

Проверка очереди выполняется существующим polling-процессом раз в минуту; второго Telegram poller нет. Карточки также доступны через кнопку `🧪 Ошибки тестировщика`.

## Команды

```bash
/home/kocher.av/.report-venv/bin/python docs/architecture/qa_agent.py run --profile full
/home/kocher.av/.report-venv/bin/python docs/architecture/qa_agent.py run --profile browser
/home/kocher.av/.report-venv/bin/python docs/architecture/qa_agent.py run --profile human
/home/kocher.av/.report-venv/bin/python docs/architecture/qa_agent.py list
/home/kocher.av/.report-venv/bin/python docs/architecture/qa_agent.py prompt QA-<ID>
/home/kocher.av/.report-venv/bin/python docs/architecture/qa_agent.py dispatch QA-<ID> -- /path/to/developer-worker
```

Состояние хранится в `qa-agent-state.json`, доказательства — в `qa-agent-evidence/<UTC timestamp>/`. Файлы создаются атомарно с режимом `0600`. Планировщик должен использовать единственную блокировку процесса и ограниченную частоту; параллельный полный прогон запрещён.

`dispatch` передаёт постановку агенту-разработчику через stdin, сохраняет его stdout/stderr и переводит задачу в `awaiting_verification`. Успешный выход разработчика не закрывает дефект: закрытие возможно только после нового прогона исходного профиля на изменённой версии.

Профиль `human` не опирается на количество unit-тестов. Он подаёт сообщения через настоящий polling бота, нажимает выданные Telegram inline-кнопки, проходит состояние диалога и фоновые задачи, а затем проверяет наблюдаемый человеком ответ и сохранённый результат. Реестр обязательных маршрутов находится в `HUMAN_JOURNEYS.json`. Любой маршрут без такой автоматизации является P1 и не позволяет объявить систему проверенной.

Каждый human-прогон сохраняет рядом три связанных файла: `receipt.json` с машинной квитанцией, `conversation-protocol.md` с дословным диалогом и проверками результата, `developer-assignment.md` с точной постановкой разработчику. QA-карточка хранит ссылки на все три документа, поэтому позднее можно сопоставить наблюдавшийся сбой с переданным исправлением.
