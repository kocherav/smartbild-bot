## Кто создаёт основную нагрузку

### Полный снимок пульта — главный источник

`hogart-scraper/dashboard/sync.py:55-75` запускает read-only цикл:

1. Все сделки страницами по 100, с большим набором полей, включая вложенные
   `financeOperations` и `invoices`.
2. Все счета страницами по 100, включая `financeOperations`.
3. Пять полных схем `/program/{id}`.

README и unit службы фиксируют внешний systemd timer каждые 10 минут. Это не
`run_singleton_background_job(...)` моста. Один успешный цикл в наблюдаемой части
12 ноября занимает примерно 3–5 минут и делает 9 страниц сделок, 8 страниц счетов
и 5 схем. Следующий timer вскоре начинает тот же полный обход заново.

Четыре сбоя со скриншота владельца совпадают именно с этим циклом (МСК = UTC+3):

| Скриншот МСК | Отправка по журналу UTC | Вызов |
|---|---|---|
| 19:53 | 16:52:16 | `GET /api/v3/invoice` → `TimeoutError` |
| 21:02 | 18:01:46 | `GET /api/v3/invoice` → `TimeoutError` |
| 22:25 | 19:24:11 | `GET /api/v3/invoice` → `TimeoutError` |
| 23:28 | 20:27:34 | `GET /api/v3/invoice` → `TimeoutError` |

Разница 44–59 секунд соответствует ожиданию ответа до клиентского таймаута. Перед
каждым сбоем видна цепочка страниц `/deal`, затем `/invoice`; после защитной паузы
следующий цикл повторяет полный обход.

### Фоновые задания моста

- `closing-documents`, `product-matching`, `procurement-intake`, `supplier-allocation`,
  `bank-reconciliation`: проверка каждую минуту, но CRM вызывается только при наличии
  очереди/работы. Массовая 10-минутная сигнатура им не соответствует.
- `proposal-status` и `procurement-status`: каждые 15 минут. Текущий код использует
  кэшированный пакет сделок; он может инициировать `deal_browser.fetch_all` при
  устаревшем/отсутствующем кэше, но не читает все счета и пять программ.
- `deal-transition-retry`: каждые 5 минут, только при непустой очереди.
- `email-payments`: каждый час; вызывает финансовые маршруты только при новом письме.
- `megaplan-protection-notice`, `installation-handoff-notifications`,
  `installation-publication`, `financial-archive`: каждые 30 секунд, но обычно
  работают локально и обращаются к CRM только при отложенной работе.
- `owner-morning-brief`: раз в день. Делает полный список сделок (обычно через кэш)
  и полный постраничный список счетов; это тяжёлый, но не постоянный источник.

### Пользовательские действия и другие тяжёлые чтения

- `deal_browser.search_any` вызывает `fetch_all`: при свежем `deal_browser_cache.json`
  поиск локальный, при отсутствии кэша — полный обход `/deal`; устаревший кэш
  обновляется отдельным фоновым процессом. Кэшировать имеет смысл и дальше, но это
  не источник показанных четырёх `/invoice` таймаутов.
- `bank_matcher.build_index`, `morning_brief._all_invoices` и
  `contract_invoice.find_invoice_number` независимо обходят весь `/invoice` по 100.
  Индекс `bank_matcher` живёт 5 минут. Эти чтения стоит объединить с одним снимком.
- `megaplan_finance.megaplan_operations` при подтверждённой финансовой записи может
  прочитать до 2 000 операций API v1 (20 страниц по 100), чтобы безопасно исключить
  дубль. Это пользовательское подтверждённое действие, а не периодический опрос;
  за окно журнал содержит 46 вызовов списка операций без ошибок.

## Защитные паузы и текущее состояние

Схема БД до `5d28828` хранит только текущее состояние, а не историю переходов.
Поэтому точные пары «защита → снова ответил» и длительность уведомлённого сбоя
восстановить нельзя. Это ограничение доказательств, а не отсутствие сбоев.

Для последнего случая можно установить:

- `/invoice` начал вызов в 20:27:34 UTC и завершился `TimeoutError` примерно через
  60 секунд; старый алгоритм открыл защиту на 30 секунд.
- `notice_times` зафиксировал уведомление защиты в 20:28:10 UTC.
- первый следующий успешный сетевой вызов — `/deal` в 20:33:13 UTC, то есть ответ
  снова получен через 5 мин 39 с после начала зависшего вызова (примерно через
  4 мин 39 с после его завершения).
- `notices.state=ok`, однако время отправки сообщения «снова ответил» перезаписываемая
  схема не хранит. Из `RECOVERY_QUIET=600` следует лишь нижняя граница: уведомление
  восстановления не могло быть раньше 20:37:34 UTC.

Текущее содержимое четырёх таблиц полностью сохранено в `current-state.json`.
Circuit не открыт (`until=0`, failures=0), notice хоста — `ok`. Есть одна старая
неопределённая запись `POST /api/v3/deal/903/applyTransition` от 2026-10-28; её нельзя
автоматически повторять без отдельного read-back. Это расследование её не меняло.

## Официальная документация

- API v1, общие правила: <https://dev.megaplan.ru/api/common.html>. Официальный
  предел: «10 запросами в секунду на аккаунт». Там же рекомендовано сохранять ключи
  авторизации, поддерживаются `ETag`/`If-None-Match`, а списки используют `Limit` и
  `Offset`.
- API v3: <https://dev.megaplan.ru/r2002/apiv3/index.html>. Для коллекций официальный
  размер страницы по умолчанию — 100; продолжение выполняется через `pageAfter` или
  `pageBefore`, а `meta.pagination.count` сообщает общий размер.
- API v1 финансовых операций: <https://dev.megaplan.ru/api/API_finance.html>.

В открытой официальной документации не найден отдельный лимит для API v3, предел
объёма ответа сверх описанной пагинации или рекомендация по клиентскому таймауту.
Поэтому переносить правило v1 «10/с» на v3 можно только как ориентир, не как
доказанный контракт v3. Наши 20/мин, 600/час и интервал 3 секунды намного строже
10/с, но они ограничивают частоту, а не стоимость запроса. Фактическая проблема —
повтор больших коллекций с тяжёлыми вложенными полями: максимум 20/мин соблюдён,
но отдельная страница всё равно не отвечает за 60 секунд.

## Рекомендации по эффекту

1. **Синхронизировать пульт раз в час или по требованию**, сохраняя последний снимок.
   При неизменном составе это уберёт до 5/6 сигнатурного трафика: около 19 240
   вызовов за неделю, или 81,6% всего журнала. Компромисс 30 минут уберёт до 15 392
   вызовов (65,2% всего журнала). Это самый сильный рычаг.
2. **Сделать инкрементальный снимок:** полный ночной обход, днём — изменения после
   `timeUpdated` и точечные карточки; программы обновлять раз в сутки. Потенциально
   устраняет почти все 23 088 повторных чтений (97,86%), оставляя объём пропорционально
   реально изменившимся сущностям. Нужен fail-closed контроль полноты и периодическая
   полная сверка.
3. **Убрать тяжёлые вложения из списков дашборда.** Не запрашивать
   `financeOperations`, `financeOperationsCount`, `invoices` на каждой сделке/счёте;
   получать их только для открытой карточки или отдельным редким проходом. Количество
   HTTP-вызовов может не измениться, но именно 91 таймаут `/invoice` и 37 `/deal`
   указывают, что надо уменьшать серверную стоимость страницы. Уменьшение `limit`
   само по себе увеличит число вызовов, поэтому применять его только если замер
   подтвердит, что меньшая страница укладывается в таймаут.
4. **Единый кэш коллекций счетов/сделок** для дашборда, `morning_brief`,
   `bank_matcher`, `contract_invoice.find_invoice_number` и `search_any`, с TTL и
   явной отметкой свежести. Это устранит независимые полные обходы и не даст
   интерактивному запросу конкурировать с синхронизацией. Для v1 использовать
   документированные ETag/304 там, где endpoint действительно их возвращает.
5. **Развести тяжёлые обходы и приоритеты:** полный снимок ночью, днём не запускать
   новый цикл после таймаута до backoff; не начинать snapshot при ожидающем
   интерактивном запросе. Текущий повтор через следующий 10-минутный timer после
   таймаута снова читает коллекцию сначала. Это не уменьшит нормальный объём само по
   себе, но уберёт каскадную конкуренцию в период деградации.
