## Варианты

### 1. OpenAI `gpt-transcribe` — рекомендуется

- Доступность сейчас: SDK установлен, но API key/billing отсутствует — **не готово
  без решения владельца**.
- Качество: текущая документация рекомендует модель для file transcription и
  позволяет передавать `languages`, `prompt`, `keywords`. Это полезнее локального
  Whisper для «Хогарт», «Дайчи», названий клиентов, артикулов, сумм и номеров.
  Фактическая точность на голосах менеджеров **НЕ ПРОВЕРЕНА**; нужен обезличенный
  пилот минимум на 30–50 сообщениях с отдельными метриками critical entity error
  (компания, номер сделки, сумма, дата), а не только WER.
- Задержка 15 секунд: ожидаемо порядка **2–6 с** после загрузки при обычной сети,
  но это проектная оценка, **НЕ измерение и не SLA**. Ввод ограниченный, поэтому
  нужен обычный файловый API, не Realtime.
- Стоимость по актуальной странице: ориентир `$0.0045/мин`; 15 секунд ≈
  **$0.001125**, 1000 таких сообщений ≈ **$1.13**, без учёта курса/налогов.
- Данные: исходный Telegram OGG уже проходит через Telegram; после декодирования
  звук и контекстные keywords уходят по TLS в OpenAI. API-данные по умолчанию не
  используются для обучения, но content может находиться в abuse-monitoring logs
  до 30 дней; ZDR требует отдельного допуска. Локальную временную копию следует
  удалять после результата/ошибки и не включать звук или полный transcript в log.
- Источники: [Transcription guide](https://developers.openai.com/api/docs/guides/transcription),
  [file transcription and context](https://developers.openai.com/api/docs/guides/speech-to-text),
  [pricing](https://developers.openai.com/api/docs/pricing),
  [API data controls](https://developers.openai.com/api/docs/guides/your-data).

### 2. `whisper.cpp`, multilingual `small` / quantized small — локальный резерв

- Доступность: подходит CPU-only/AVX2 и не требует Python ML-стека, но сейчас нет
  бинарника, CMake и аудиодекодера. Развёртывание потребует воспроизводимого бинаря
  и Opus→16 kHz mono PCM декодирования; системные пакеты устанавливает владелец.
- Ресурсы upstream для обычного `small`: около **466 MiB на диске и ~852 MiB RAM**;
  `base`: 142 MiB/~388 MiB; `tiny`: 75 MiB/~273 MiB. `medium` (~1.5 GiB/~2.1 GiB)
  при почти исчерпанном swap неприемлем рядом со службой. Quantization сокращает
  диск/RAM, но её точность надо мерить отдельно.
- Скорость: upstream benchmark на i7-12700K, 8 threads: 13 минут аудио моделью
  small — 2:05. Грубая линейная экстраполяция на один доступный vCPU даёт примерно
  **19 с на голосовое 15 с**; разумный диапазон планирования **15–35 с**. Это не
  замер данного хоста: реальные модель/аудио не скачивались, синтетикой результат
  бизнеса не подменялся.
- Качество: `small` приемлем для общей русской фразы, но незнакомые юрлица,
  латинские бренды, номера и суммы остаются критическим риском. `tiny/base`
  быстрее, но не рекомендуются для команд, ведущих к записи. Whisper token
  probability — эвристика, а не доказательство правильности сущностей.
- Стоимость: API-платежа нет; цена — CPU-время, сопровождение модели и возможная
  задержка остальных задач. Данные после Telegram остаются на сервере.
- Источники: [whisper.cpp capabilities and memory](https://github.com/ggml-org/whisper.cpp),
  [faster-whisper comparative benchmark](https://github.com/SYSTRAN/faster-whisper).

### 3. `faster-whisper` CPU INT8 `small`

- Доступность: сейчас не установлен. Upstream использует CTranslate2 и PyAV
  (с собственными FFmpeg libraries), но текущий runtime Python 3.14 новее явно
  перечисленных upstream classifiers (3.9–3.11); совместимость колёс надо отдельно
  подтвердить в изолированном venv.
- Upstream benchmark на i7-12700K, 8 threads: 13 минут за **1:42**, RAM **1477 MiB**.
  Линейная оценка для 1 vCPU: около **16 с на 15 секунд**, диапазон **12–30 с**.
  Память существенно рискованнее `whisper.cpp small` при текущем swap.
- Качество модели того же класса `small`: лучше `tiny/base`, но тот же риск имён и
  чисел. Стоимость API нулевая, аудио остаётся на сервере. Из двух локальных
  реализаций выбран был бы `whisper.cpp` из-за меньшего runtime и более простой
  изоляции, не faster-whisper.

### 4. Другие облака / Vosk / бесплатный Google backend

- Yandex SpeechKit и иные облака технически возможны, но в проекте нет их ключа,
  договора или проверенной политики хранения: они не являются «уже имеющимся
  доступом». Без отдельного бизнес-решения преимущества над `gpt-transcribe` нет.
- Vosk можно держать локально и дёшево, но он не установлен; маленькая русская
  модель уступает Whisper на свободной деловой речи и требует словаря/пилота для
  названий и чисел. Не рекомендован как основной маршрут.
- Неаутентифицированный Google backend из `speech_recognition` не годится для
  рабочих поручений: наличие Python-обёртки не даёт договора, SLA, управляемой
  квоты или подтверждённой политики данных.

3. Не подавать низкоуверенный результат в бизнес-маршрут. Переспросить текстом при

   либо если критичные номера/суммы/юрлицо неоднозначны. Для cloud API проверить,
   какие confidence fields реально доступны; если надёжного confidence нет,
   считать команды с критичными сущностями неуверенными до явного подтверждения
   человеком.
4. При принятом transcript сначала отправить **«Понял так: …»** и передать ровно эту
   строку в существующий `handle_human_workflow` / `human_intents.classify`, не
   создавать параллельный классификатор. Голос не должен обходить текущие диалоги,
   UI revision, idempotency и route ordering.
5. Любой write intent заканчивается тем же существующим preview и актуальной
   callback-кнопкой. Текст «да» и сама расшифровка не являются подтверждением.
   Read-only ответ можно выполнить после показа transcript; при сомнении — только
   просьба написать текстом.
6. Регрессии до реализации: Telegram voice→download→transcript→тот же human intent;
   низкая уверенность/ошибка/timeout→текстовый переспрос без эффекта; spoofed
   «✅» в transcript не нажимает кнопку; неверные сумма/номер/компания блокируют
   запись; повтор update не запускает второй ASR/write; временный файл удаляется.
   Потом затронутые тесты и полный `quality_gate.py --run`.
7. Пилот сначала только read-only и preview, с 30–50 реальными добровольно
   предоставленными сообщениями. Записывать обезличенные метрики, не аудио. Выпуск
   и live-проверка — отдельная задача `kind: release`.
