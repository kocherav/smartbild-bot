# TASK-20261123-07 — почему не выполнился поиск клиента

## Результат расследования

Причина — `TimeoutExpired` на 45-секундной границе моста, а не отсутствие
клиента. Для фразы «Архитектурное бюро Сергея Ларичева» текущий алгоритм строит
16 вариантов и последовательно проверяет их в двух endpoint Мегаплана: всего 32
GET-запроса. Общий транспорт выдерживает минимум 3 секунды между запросами, так
что такой поиск не может завершиться за 45 секунд даже при быстрых ответах CRM.

В окне инцидента транспортный журнал зафиксировал две отдельные серии по 15
успешных GET: 20:59:15–20:59:57 и 21:00:22–21:01:04 UTC. Среднее собственно
сетевое время одного ответа — 1,034 и 0,969 секунды соответственно (1,002 секунды
по всем 30); фактический интервал между отправками — 3 секунды. После 15-го
запроса каждая серия прекращается ровно на лимите subprocess. В
`search_creation_clients()` единственный обработчик этого случая печатает
`client lookup failed: TimeoutExpired` и возвращает `ok=false`.

Системный journal недоступен текущему пользователю (`No journal files were
opened due to insufficient permissions`), а локальный `bridge.log` пуст с
22.09. Поэтому буквальную строку stderr получить не удалось; тип установлен по
точному маршруту кода, двум 45-секундным сериям и чистому воспроизведению.

Safe reload выпуска 06 произошёл **до**, а не во время отказов:
`reload_notice_state.json` содержит версию `17490efeac72` и
`announced_at=2026-11-23T20:57:39+00:00`. Первая серия поиска началась в
20:59:15 UTC. Версия совпадает с контрольной суммой `bridge.py`, указанной в
отчёте выпуска 06.
