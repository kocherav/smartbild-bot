# Задание внешнему тестировщику: неверная привязка проектов между сделками 865 и 888

Дата передачи: 2026-11-07  
Постановщик: **задание дал владелец SmartBild**.  
Приоритет: **P1** — файл одной сделки стал активным проектом другой сделки.  
Контур: `MNT-PREP`, Telegram → карточка сделки → «Монтаж сделки» → «Приложить проект» → «Загрузить новый файл» → Мегаплан / реестр монтажей / OneDrive.

## 1. Поручение владельца

Независимо разобрать весь инцидент, проверить достаточность системного исправления и объяснить,
почему существующие проверки не обнаружили перенос контекста между сделками. Проверить не только
номера 865/888, а общий класс ошибок: в одном Telegram-чате текущая карточка одной сделки, а
сохранённый контекст монтажа — другой.

Не выполнять хозяйственные записи в боевом Мегаплане. Для проверок с записью использовать стенд
или двойник CRM. Реальные сделки 865/888 разрешено только перечитывать.

## 2. Как проявился дефект

Владелец находился в карточке сделки **865**, открыл раздел монтажа, выбрал «Приложить проект» →
«Загрузить новый файл» и отправил PDF проекта ЖК РЕноме. Бот ответил:

> ✅ Файл сохранён как проект версии №2.

После этого в кабинете монтажника появилось уведомление:

> 📐 По сделке №888 опубликована новая версия проекта №2.

В карточке монтажа 888 бот показывал проект как привязанный. То есть интерфейс пользователя
показывал сделку 865, но внешний эффект был выполнен для сделки 888.

Это был повторный перекрёстный инцидент. Днём ранее проект **ул. Ильинка**, относящийся к 888,
ошибочно стал активной версией проекта сделки 865.

## 3. Подтверждённое состояние чата в момент расследования

В `deal_ui_state` одного и того же Telegram-чата одновременно находились:

```json
{
  "current_deal_id": "865",
  "installation_deal_id": "888",
  "pending": null
}
```

Код вычислял цель монтажных действий как:

```python
installation_deal_id = state.get("installation_deal_id") or current_deal_id
```

Поэтому устаревший `installation_deal_id=888` имел приоритет над реально открытой карточкой
`current_deal_id=865`. На шаге получения документа применялся ещё один опасный fallback:

```python
project_deal_id = installation_deal_id or current_deal_id
```

Цель загрузки не фиксировалась в момент нажатия кнопки и могла быть определена из смешанного
состояния уже после получения файла.

Комментарии Мегаплана с ошибочными вложениями:

- сделка 865: комментарий **20198**, файл **90051**;

API вернул для этих комментариев только `possibleActions=["act_read"]`; удалить их через
доступный API нельзя. Они оставлены как исторические вложения, но исключены из активных проектов
монтажного контура.

## 5. Проверка идентичности файлов

Копии из OneDrive перечитаны и сверены SHA-256:

```text
ЖК РЕноме:
cd33c831df41f59aa9d2d8d8a0ed46f674715546fb488798216374e90fece381
865 версия 2 == ошибочная 888 версия 2

ул. Ильинка:
d5064149de6a7001e153d7b8e2475d19d1a1aca3a053d279d76d277fde1a190f
888 версия 1 == ошибочная 865 версия 3
```

Следовательно, для восстановления не требовалось повторно загружать документы или создавать
новые версии: правильные байты уже были в правильных сделках.

## 6. Восстановление данных

В одной транзакции с записью в `audit_log`:

- у 865 активирована версия 2, файл 90050 «ЖК РЕноме»;
- у 888 активирована версия 1, файл 89986 «ул. Ильинка»;
- ошибочные версии 865/3 и 888/2 переведены в `archived`, физически не удалены;
- создана резервная копия реестра в OneDrive.

Повторное чтение после safe reload подтвердило ровно по одной активной версии:

```text
865 → version_no=2, megaplan_file_id=90050, ЖК РЕноме
888 → version_no=1, megaplan_file_id=89986, ул. Ильинка
```

## 7. Реализованное системное исправление

1. Новый маршрут «📐 Приложить проект» берёт сделку только из открытой карточки
   `current_deal_id`, не из старого монтажного состояния.
2. При нажатии «📤 Загрузить новый файл» целевой номер фиксируется отдельно в
   `installation_project_upload_deal_id`.
3. При получении документа разрешён только этот зафиксированный ID.
4. Старое незавершённое состояние без `installation_project_upload_deal_id` работает
   fail-closed: файл никуда не прикрепляется, пользователь получает указание открыть нужную
   сделку заново.
5. После успешной загрузки зафиксированный ID очищается.

Добавлена регрессия `telegram-bridge/test_installation_project_context.py`:

- карточка 865 + устаревший монтажный контекст 888 → запрос файлов только для 865;
- зафиксированная цель загрузки не меняется из-за других ID в состоянии;
- legacy-состояние без зафиксированной цели не получает fallback.

Целевые проверки: **11/11**.  
Полный изолированный quality gate: **1339/1339**, квитанция
`2026-11-07T14:07:41.617160+00:00`.  
Сервис после safe reload: active, `NRestarts=0`.

Живая повторная загрузка файла намеренно не выполнялась: она создала бы ещё одну хозяйственную
версию. Поэтому тесты подтверждают механику, а реальный маршрут новой записи после исправления
пока **НЕ ПРОВЕРЕН**.

## 8. Почему прежние проверки пропустили дефект

Текущие тесты использовали согласованное состояние: `current_deal_id` и
`installation_deal_id` относились к одной сделке либо существовал только один из них. Не было
сценария «открыли монтаж 888 → вернулись в сделки → открыли 865 → начали загрузку проекта».
Также граница между кнопкой и последующим Telegram-документом проверялась как два удобных шага,
но не как одна операция с неизменяемым целевым ID.

## 9. Обязательное задание тестировщику

1. На стенде воспроизвести точную последовательность переключения 888 → 865 и убедиться, что
   файл попадает только в 865.
2. Повторить зеркально 865 → 888.
3. Между кнопкой «Загрузить новый файл» и отправкой документа открыть другую сделку или нажать
   навигацию; цель не должна молча измениться. Ожидаемый результат: либо исходная зафиксированная
   сделка, либо явная безопасная отмена согласно контракту UI.
4. Отправить два документа подряд, повтор Telegram update и документ после перезапуска сервиса;
   проверить отсутствие дублей и неверной сделки.
5. Проверить старую кнопку из сообщения, созданного до переключения сделки: устаревшее действие
   не должно получить новый контекст.
6. Проверить соседние монтажные маршруты на тот же класс дефекта: контакт объекта, ведомость,
   выплата монтажнику, передача в монтаж, новый отчёт. Если они используют приоритет старого
   `installation_deal_id`, оформить отдельный P1, а не расширять вывод без доказательств.
7. Проверить раздельно три внешних результата: файл в Мегаплане, активная версия в SQLite,
   копия в правильной папке OneDrive. Сообщение Telegram само по себе успехом не считать.
8. Проверить восстановление 865/888 только чтением и убедиться, что архивные ошибочные версии
   не выдаются монтажнику как активные.
9. Оценить, достаточно ли текущего ключа операции, или необходим общий `operation_id + deal_id +
   file_unique_id` для защиты от повторной доставки Telegram.
10. Добавить постоянную сквозную регрессию в QA-матрицу для переключения между двумя сделками.

## 10. Формат ответа тестировщика

Создать в GitHub файл:

`handoff/review-requests/PROJECT-CONTEXT-865-888-20261107-QA-REVIEW.md`

В ответе указать:

- `status: passed | failed | blocked`;
- какие маршруты исполнены на стенде и какие только просмотрены;
- доказательства по Telegram / CRM / SQLite / OneDrive отдельно;
- найденные соседние маршруты с тем же риском;
- почему прежняя QA-матрица пропустила дефект и что в неё добавлено;
- нужны ли дополнительные исправления до закрытия P1;
- коммиты и ссылки, реально опубликованные в GitHub.

Задание считается закрытым только после независимой проверки тестировщиком. Сам факт наличия
исправления и зелёного unit/quality gate не является сквозной приёмкой.
