# Обмен заданиями: AI-тестировщик → разработчик

Тестировщик (Claude) кладёт задание файлом в `inbox/`; бот на сервере сам его
находит и передаёт Codex-разработчику; разработчик отвечает отчётом в `outbox/`.
Владелец ничего не пересылает вручную, но выпуск подтверждает кнопкой.

## Как это работает

1. Тестировщик коммитит `handoff/inbox/TASK-ГГГГММДД-NN.md` в свою ветку `claude/*`
   (или задание попадает в `main`).
2. Бот раз в 15 минут (`QA_SCHEDULE.json` → `handoff`) делает `git fetch` и читает
   файлы через `git show`. Ветки он не переключает и код из них не запускает.
3. Задания вида `code`, `tests`, `docs`, `investigation` сразу уходят разработчику.
   `release` и любое задание с `requires_owner: yes` ждут кнопки владельца
   «✅ Выполнить TASK-…» (если кнопки не видно: «☰ Ещё → 🧪 Ошибки тестировщика»).
4. Каждая версия файла выполняется один раз. Исправленный файл (новая версия того же
   `id`) передаётся заново после завершения текущей работы.
5. Код автоматический разработчик отправляет только в ветку `handoff/TASK-…`. В `main`
   сливает человек: владелец или сопровождающий разработчик — сами, либо через
   задание `kind: release`, подтверждённое кнопкой владельца (решение владельца от 23.10).
   Разработчик обязан закоммитить в `main` отчёт `handoff/outbox/TASK-….md` и
   отправить его в GitHub.
6. Слова разработчика — не доказательство. После его работы бот сам читает GitHub:
   отчёт должен лежать в `main`, а каждый коммит из строки `commits:` — существовать и
   быть опубликованным. Владелец получает «✅ отчёт подтверждён в GitHub» или
   «⚠️ НЕ подтверждён» с причиной (23.10 разработчик назвал три несуществующих коммита).

Перед текстом задания бот всегда добавляет неизменяемые правила: протокол
разработки, запрет хозяйственных записей, рассылок, изменения прав и force-push,
выпуск только по `release`. Задание не может их отменить.

Изменённый файл задания бот считает новым решением и после выполнения предлагает его снова.
Поэтому тестировщик **не правит задание после того, как оно отправлено** (25.10 правка
TASK-20261025-03 во время выпуска привела к повторному запуску): любая доработка, повтор после
блокировки или уточнение — новое задание с новым `id`.

Состояние обработки хранится на сервере: `telegram-bridge/handoff_state.json`
(вне Git). Неверно оформленный файл не выполняется; владелец получает одно сообщение.

## Формат задания

```markdown
---
id: TASK-20261023-01
kind: code
priority: P1
title: Короткое название
summary: Что делаем и зачем, простыми словами — это владелец читает первым.
branch: claude/stoic-tesla-x1nd0e
requires_owner: no
---

Что сделать, зачем, где воспроизводится, критерии готовности.
```

| Поле | Обязательно | Значения |
|---|---|---|
| `id` | да | `TASK-ГГГГММДД-NN`, совпадает с именем файла |
| `kind` | да | `code`, `tests`, `docs`, `investigation`, `release` |
| `title` | да | одна строка |
| `summary` | желательно | 1–2 фразы для владельца: что делаем, что чиним; показывается первым во всех сообщениях |
| `priority` | нет | `P1`, `P2`, `P3` |
| `branch` | нет | ветка с изменениями, которую нужно слить |
| `requires_owner` | нет | `yes` — ждать кнопки владельца даже для кода |

## Формат отчёта (`outbox/TASK-….md`)

```markdown
status: done            # done | blocked | needs_owner
commits: 572ecaa, …
checks: quality_gate 1160/1160; human 62/62
not_done: …
evidence: реализовано / проверено изолированно / выпущено / подтверждено в работающей системе
question: (только для needs_owner) один конкретный вопрос владельцу
```
